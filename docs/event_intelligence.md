# Event-Aware Intelligence Module Architecture

This document describes the design and integration of the **Event-Aware Intelligence** module in ParkZenith, which dynamically adjusts occupancy forecasting, arrival availability, recommendations, and queue models based on external events.

---

## 2. Event Models & Schemas

### ORM Model (`Event`)
- **Table name**: `events`
- **Fields**:
  - `event_id`: Unique identifier (string, uuid)
  - `name`: Event name (e.g. "Football Match")
  - `type`: Event category (e.g. Concert, Sports Event)
  - `location_name`: Flat string address/venue
  - `latitude` / `longitude`: Coordinates
  - `radius_of_influence`: Influence distance in km
  - `expected_attendance`: Total expected attendees
  - `start_time` / `end_time`: Timestamps
  - `confidence_score`: 0.0 to 1.0 confidence indicator
  - `predicted_extra_demand`: Baseline demand spike percentage
  - `congestion_multiplier`: Baseline congestion factor

### Pydantic Schemas
- `EventLocation`: nested model mapping event coordinate limits.
- `Event`: response serialization model.
- `EventCreate` / `EventUpdate`: request validation models.
- `EventImpact`: estimated travel delay, demand surge, and wait increments on a facility.
- `EventForecast`: event-adjusted forecast response.
- `EventRecommendation`: event-adjusted recommendation detail.
- `EventAnalytics`: report detailing predicted overflows and timeline surges.

## 3. Impact Engine Logic

The `EventImpactEngine` estimates event effects on facilities based on physical distance and temporal proximity:

### 1. Distance Decay
If distance $d$ between facility and event is within the event's radius of influence $R$:
$$\text{decay} = \frac{R - d}{R}$$
Otherwise, decay is $0.0$.

### 2. Temporal Weighting
Impact window starts 2 hours before event start and ends 2 hours after event end:
- **Ramp-up** (2h before start): linearly ramps up weight from $0.0$ to $1.0$.
- **Plateau** (during event): weight remains steady at $1.0$.
- **Ramp-down** (2h after end): linearly ramps down weight from $1.0$ to $0.0$.

### 3. Composite Calculation
$$\text{Extra Occupancy \%} = \text{Base Occupancy} \times \text{decay} \times \text{time\_weight} \times \text{attendance\_scale} \times \text{confidence}$$

## 4. Integration Details

### Forecasting Service
Occupancy predictions dynamically aggregate the extra demand generated by all active events near the target facility, clamping the final prediction to $[0\%, 100\%]$.

### Recommendation Service
Scores are divided by the composite event congestion multiplier. Reason strings are dynamically updated to flag event-related delays, suggesting alternative zones and recommending $30\text{-minute}$ earlier arrivals.

### Queue Service
Queue wait times and length are multiplied by the composite congestion factor. The arrival and departure rates are scaled up during event inflow (arrival) and outflow (departure) peaks.

## 5. API Reference

- `POST /events`: Create an event
- `GET /events`: List all events
- `GET /events/upcoming`: Retrieve upcoming events
- `GET /events/active`: Retrieve currently active events
- `GET /events/{id}/impact`: Fetch single event impacts across facilities
- `GET /events/forecast`: Retrieve event-adjusted forecasts
- `GET /events/recommendations`: Retrieve event-adjusted recommendations
- `POST /events/simulations`: Seed scenario datasets (e.g. `concert`, `football match`)
- `GET /events/analytics`: Retrieve composite overflow risk dashboard metrics
